# 资产快照

工作流：复用全局登录与庭院皮肤预设 → 庭院 → 纳物库 → 读取 → 庭院 → 保存历史。

## 执行

在 OAS 工作目录执行：

```powershell
python -m tasks.AssetSnapshot.script_task --config 绘卷
```

也可以在日常任务中的“资产快照”配置调度器。任务默认关闭，默认成功/失败间隔沿用通用 Scheduler。
设备、登录角色、庭院皮肤和异常处理使用所选配置的全局设置，不需要独立复制账号配置。

## 分组和历史

- 无有效完整历史时选择“综合”，全量扫描，未识别材料输出 0。
- 已有历史时选择“最近”，只替换本次成功识别的数量，未出现或 OCR 失败的材料保留历史数量。
- “最近”首屏顶部有说明，后续格子布局与“综合”一致。两个分组共用模板匹配和滑动流程，数量 ROI 按命中位置计算。
- 顶部金币、体力、勾玉、魂玉每次读取，独立于材料图标匹配。
- 顶部体力读数仅用于确认已识别到体力，最终数量来自详情弹窗：在图标和右侧数字区域 `(674,16,143,30)` 内随机点击一次，排除右侧“+”；核对弹窗标题“体力”，读取“已拥有”的整数，两次连续一致后采用精确数量（例如 60994，不使用顶部约数 6.1 万）。已有体力弹窗时直接读取；读取后点击右侧空白处并确认弹窗关闭，再继续扫描。读取或关闭失败均中止保存并保留旧历史。
- 顶部货币要求整段 OCR 文本为数字和可选的万/亿/千单位（支持规范千位分隔符）。如“皖838”等混合文本会被拒绝，不能截取为 838；异常时最多重试两次，每次重新截图并调整裁切，仍失败则中止本轮保存并保留旧历史。普通货币备用裁切保持完整数字宽度，魂玉沿用仅确认 0 的窄裁切。
- 顶部货币日志记录原始文本、数量、裁切区域和尝试次数，便于定位误读。更新并重启脚本后重新运行资产快照，可覆盖之前保存的错误数量。
- 只有扫描完成且返回庭院成功才原子保存历史；达到扫描上限会报错并保留旧文件。
- 历史保存在 `config/asset_snapshot/<身份哈希>.json`，按配置名、设备 serial、配置的登录角色隔离。
- 手动在同一配置中切换未配置名称的角色时，应开启“始终全量读取”重建历史，避免混用数据。
- “最近”游戏规则为近 30 天获得的前 100 种物品，不保证显示所有已消耗至 0 的材料。需要刷新这类数据时开启“始终全量读取”。

## 配置

`config/template.json` 中的 `asset_snapshot` 使用 `scheduler` 和 `asset_snapshot_config` 两个分组：

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| force_full_scan | false | 关闭时自动选择首次综合、后续最近；开启时每次综合 |
| max_reset_swipes | 3 | 顶部复位最多 3 次 |
| max_scan_swipes | 10 | 向下最多滑动 10 次，首屏另计 |
| match_threshold | 0.95 | 材料模板通过分数 |

滑动端点带随机偏移，每次松手后等待惯性并检测稳定帧。重叠页面同一材料采用本轮更高匹配分数的有效 OCR 结果。

## 输出

历史文件的 `snapshot` 保留 OASX 预留格式：`status`、`updatedAt`、`values`。
`values` 使用 `asset_snapshot_variables.json` 的 73 个变量名。
已移除错误模板的 `eternal_divine_talisman` 保留字段并输出 0。
匹配日志 `log/asset_snapshot_material_match_scores.json` 保存分组、各页分数和实际读到的数量。
本任务没有改动 OASX 页面或添加采集 HTTP API。

模板通过分数不能替代数量 OCR 的正确性校验；相似材料误匹配和数字漏位仍需结合匹配日志核对。

## 皮肤券与 SP 皮肤券

两种券共用主体模板查找候选格子（门限 0.90），通过 NMS 去除同格重复候选，然后在每个候选内比较两种原模板和右下角 SP 标记。

- SP 标记门限为 0.80；普通券要求标记分数不高于 0.45，且普通模板比 SP 模板至少高 0.03。标记缺失、区域不完整或分数冲突时不直接判为普通券。
- 普通券沿用格子数量 OCR。SP 券使用右侧详情数量，避免图标中的 SP 字样被识别为额外数字，也避免窄裁切截断多位数量。
- 无法确定类型时点击候选格子，检查青色选中边框，以右侧完整名称和数量连续两次一致的结果确认。详情失败会中止本轮保存，保留旧历史。
- 本轮已确认的详情数量会缓存，重叠页面不重复读取。原模板分数只标为 `candidate`，最终判定单独记录为 `skin_ticket_verification`，包含主体、两种模板、SP 标记分数及数量。
- 主体模板 `assets/skin_ticket_body.png` 为 67×45；标记模板 `assets/sp_ticket_badge.png` 为 30×17，均从现有 SP 券完整格子裁切，不包含数量。详情名称区域为 `(855,110,250,39)`，详情数字区域为 `(930,148,180,36)`。

万象之魄的数量区域单独使用相对格子 `(67,70,27,23)`，避开“万能”文字。其余材料保持默认数量区域。

同步代码后需重新启动脚本进程，以加载新增规则及模块。

## 资产变化与七天统计（2026-11-02）

- 成功快照同时进入 `config/asset_snapshot/history.sqlite3`，原身份 JSON 保留为最新兼容导出；导出失败不撤销数据库提交，下次读取会重试修复。
- 既有合法 JSON 只迁移一份，逐项标为旧版本数据，不能还原此前已覆盖的历史。迁移后首次采集使用综合，具有两次新版有效观测后才显示较上次差值。
- 每项记录本轮读取/沿用/未确认/不支持、实际观测时间与精确/约数精度。综合扫描漏读不视为确认耗尽；此前为正的漏读材料会再扫描复查，仍不能确认的保留最后已知数及质量状态。
- OASX“刷新资产”提交一次真实采集，不依赖周期任务开关，也不改变 enable/next_run。脚本停止时运行单次工作进程；脚本运行时在任务安全边界处理，同设备互斥。两个入口和网络重试不会重复创建同一请求。
- 七天采用 UTC+8 今天及前六个自然日，并额外查询基准日。每日变化需要相邻两日有效采样，完整七天变化需要基准日与今天两端；缺测保持 null，部分区间另行标明。折线按用户要求连接缺测前后的有效点，不生成缺测点或补零。
- 新增 `full_scan_interval_hours`（默认0，建议24）和 `history_generation`（默认0；手动换未配置名称的角色时递增以隔离历史）。
- GET `/{script}/asset_snapshot?compare=previous|seven_days`；GET `/{script}/asset_snapshot/history?asset=gold&days=7`；POST `/{script}/asset_snapshot/captures` 的 JSON body 为 `{"idempotencyKey":"客户端生成的唯一键"}`；GET 返回的 statusUrl 可查询排队、运行及最终结果。

升级需重启 OAS 服务与脚本进程，并使用新版 OASX。历史库无需人工创建或改动现有账号配置。
